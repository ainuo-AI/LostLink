# 核心用户流程

> 状态：认证、详情、图片发布、个人管理、举报、匹配反馈和管理审核已完成前后端联调。
>
> 最后核对：2026-10-06

本文描述跨页面、跨前后端的用户流程。具体页面状态和视觉规则见 [设计资料](../design/README.md)，范围与验收要求见 [需求与范围](requirements.md)。

## 当前可验证流程

当前已实现以下基于后端和 MySQL 的流程：

1. 用户打开首页，前端向后端请求失物和拾物记录。
2. 用户按关键词、类别、校区、时间和记录类型筛选，筛选条件由后端执行。
3. 用户点击记录卡片进入 `/items/:id` 独立详情页，查看类别、地点、时间和联系提示。
4. 用户切换分页；没有符合条件的记录时，页面显示空状态并允许清除筛选。
5. 请求失败时，页面显示错误信息并允许重试。

6. 用户可以注册和登录；受保护页面会在刷新时向后端确认当前会话。
7. 登录用户通过 `/publish/lost` 或 `/publish/found` 发布真实记录，并在 `/my` 查询、编辑、完成或关闭自己的记录。
8. 用户退出后，当前服务端会话被吊销，本地会话同步清除。

详情页下方的“举报”进入 `/items/:id/report`。举报原因和说明通过前端校验后写入后端审核队列，管理员可处理或隐藏关联内容。图片在发布时上传；完整联系方式只在所有者管理视图中返回。

## 当前图片与匹配流程

1. 发布表单的未提交草稿保存于 `localStorage`，所选图片在提交前暂存于 IndexedDB；提交时先上传图片，再将服务端编号与物品关联。
2. 新物品发布后，后端检索相反类型的进行中候选，按类别、校区、区域、时间和文本生成解释分数，并为双方所有者创建去重通知。
3. 用户打开 `/notifications` 查看服务端通知；进入 `/notifications/:id` 可比较候选并确认或拒绝。已读和反馈是相互独立的服务端状态。

综合分只用于候选排序，不是找回概率；确认候选不代表完成认领或归还。当前通知只在站内展示，没有接入短信、邮件或推送服务。

## 已实现的服务端发布流程

1. 用户登录并选择“发布失物”或“登记拾物”。
2. 用户填写类别、时间、地点、描述和联系方式，并可选择最多三张图片。
3. 前端完成基础校验，后端再次执行格式、权限和安全校验。
4. 后端将所有者固定为当前登录用户，保存记录，并在所有者响应中返回管理字段。
5. 页面显示发布结果；失败时保留可恢复的输入并给出明确原因。

后端只接受属于当前用户且未被其他记录占用的 `image_ids`；完整联系方式只向所有者或管理员返回。校园统一身份方式和认领核验规则仍待确认。

## 已实现的搜索与匹配流程

1. 用户浏览或搜索公开记录。
2. 后端根据筛选条件返回稳定分页的结果。
3. 系统为某条失物或拾物信息生成候选匹配，并说明主要匹配依据。
4. 用户将候选标记为有帮助、不相关或已确认。
5. 反馈被记录，用于后续评估和校准匹配策略。

候选匹配只提供线索，不自动判定物品所有权。外部 AI 不可用时，基础发布与搜索能力应继续工作。

## 已接入的记录关闭流程

1. 用户通过受控方式联系相关发布者并进行线下核验。
2. 发布者将记录更新为已找回、已归还或已关闭。
3. 系统在状态更新事务中记录操作者、原状态、新状态、原因和时间。
4. 公开列表默认不再展示失效记录，个人信息按保留策略处理。

待确认：认领和所有权核验流程、联系方式向其他用户展示的条件、审计与业务数据保留期限。

## 异常和边界状态

每条正式流程在实现前至少定义：

- 未登录或无权限。
- 输入无效、重复提交或资源不存在。
- 搜索无结果。
- API、数据库或外部服务失败与超时。
- 用户取消操作或网络中断后的恢复方式。
- 涉及个人信息时的隐藏、删除和审计行为。

流程成为实现任务前，应把待确认项落实到需求编号、接口契约和可验证的验收条件中。
