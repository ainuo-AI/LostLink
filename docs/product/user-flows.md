# 核心用户流程

> 状态：首页只读浏览已接入真实 API 与数据库；发布、举报和匹配反馈仅有浏览器本地演示，认证与状态闭环仍未实现。
>
> 最后核对：2026-10-02

本文描述跨页面、跨前后端的用户流程。具体页面状态和视觉规则见 [设计资料](../design/README.md)，范围与验收要求见 [需求与范围](requirements.md)。

## 当前可验证流程

当前已实现基于后端和 MySQL 数据的只读浏览流程：

1. 用户打开首页，前端向后端请求失物和拾物记录。
2. 用户按关键词、类别、校区、时间和记录类型筛选，筛选条件由后端执行。
3. 用户点击记录卡片进入 `/items/:id` 独立详情页，查看类别、地点、时间和联系提示。
4. 用户切换分页；没有符合条件的记录时，页面显示空状态并允许清除筛选。
5. 请求失败时，页面显示错误信息并允许重试。

详情页下方的“举报”进入 `/items/:id/report`。举报原因和说明通过前端校验后保存在当前浏览器，不进入后端或管理员工作流。首页流程不包含账号、写入 API、服务端文件上传或真实联系方式；当前数据库内是幂等脚本生成的演示记录。

## 当前前端本地演示流程

1. 用户通过顶部或手机导航进入 `/publish/lost` 或 `/publish/found`，填写物品、地点、时间和联系信息。拾物登记另需填写保管方式、地点与可联系范围。
2. 前端校验必填项、时间和联系方式；可选 JPG、PNG、WebP 图片，暂定每张不超过 5MB、最多 3 张。失物与拾物草稿分开存于 `localStorage`，图片存于 IndexedDB。
3. 提交成功后生成 `demo-` 前缀的本地记录编号与“待匹配”演示状态。公开摘要只保存脱敏联系方式；记录不会发送给后端，也不会进入首页真实列表。
4. 用户打开 `/notifications` 查看预置演示通知，按已读及处理状态筛选；进入 `/notifications/:id` 可比较候选信息并确认或拒绝。已读与处理状态分别保存，刷新后保留。

通知、候选和分数由前端预置，未从新发布记录计算，也未发送真实通知。综合分不是找回概率；确认候选不代表完成认领或归还。浏览器存储损坏、不可用或容量不足时，页面显示错误，不能把本地写入失败当作成功。

## 计划中的服务端发布流程

1. 用户登录并选择“发布失物”或“登记拾物”。
2. 用户填写类别、时间范围、地点范围和描述，并按规则选择是否上传图片。
3. 前端完成基础校验，后端再次执行格式、权限和安全校验。
4. 后端保存记录并返回公开可见的数据。
5. 页面显示发布结果；失败时保留可恢复的输入并给出明确原因。

待确认：校园身份验证方式、图片要求、联系方式可见条件和内容审核规则。

## 计划中的真实搜索与匹配流程

1. 用户浏览或搜索公开记录。
2. 后端根据筛选条件返回稳定分页的结果。
3. 系统为某条失物或拾物信息生成候选匹配，并说明主要匹配依据。
4. 用户将候选标记为有帮助、不相关或已确认。
5. 反馈被记录，用于后续评估和校准匹配策略。

候选匹配只提供线索，不自动判定物品所有权。外部 AI 不可用时，基础发布与搜索能力应继续工作。

## 计划中的认领与关闭流程

1. 用户通过受控方式联系相关发布者并进行线下核验。
2. 发布者将记录更新为已找回、已归还或已关闭。
3. 系统记录必要的状态变化和关闭原因。
4. 公开列表默认不再展示失效记录，个人信息按保留策略处理。

待确认：联系信息展示机制、所有权核验提示、状态枚举、审计信息和数据保留期限。

## 异常和边界状态

每条正式流程在实现前至少定义：

- 未登录或无权限。
- 输入无效、重复提交或资源不存在。
- 搜索无结果。
- API、数据库或外部服务失败与超时。
- 用户取消操作或网络中断后的恢复方式。
- 涉及个人信息时的隐藏、删除和审计行为。

流程成为实现任务前，应把待确认项落实到需求编号、接口契约和可验证的验收条件中。
