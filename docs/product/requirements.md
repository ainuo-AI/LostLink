# 需求与范围

> 状态：草案，需团队评审。本文是产品范围的主要入口；确认后的需求应拆分为 Issue，并保留需求编号便于追踪。
>
> 实现状态核对：2026-10-06；下述建议范围不等于已交付范围。

## 1. 项目背景

校园失物招领信息经常分散在群聊、表单和线下公告中，难以检索、更新和追踪。LostLink 希望提供统一的信息发布和查找入口，并通过候选匹配减少人工浏览成本。

## 2. 项目目标

- 让用户能够规范地发布失物和拾物信息。
- 让用户能够通过关键字段检索和筛选信息。
- 给出可解释的候选匹配，辅助用户建立联系和核实。
- 让信息拥有明确状态，减少长期存在的无效记录。

系统只辅助信息发现和沟通，不保证物品归属，也不能替代线下身份与所有权核验。

## 3. 用户角色

| 角色 | 主要需求 |
| --- | --- |
| 普通用户 | 发布、浏览、搜索、管理自己的信息，查看候选匹配并反馈结果 |
| 管理员 | 处理举报、限制或恢复普通用户、查看审计并管理匹配校准版本 |

当前允许游客浏览公开物品；校园身份认证和管理员授予流程仍需团队确认。管理员业务接口已经实现，但不代表角色授予和运营制度已经定稿。

## 4. 第一阶段建议范围

以下是 MVP 候选范围，不代表已经确认：

### R-01 用户身份

- 用户可以注册、登录和退出。
- 用户只能修改和关闭自己发布的信息。
- 未登录用户的可见范围由团队在实现前确认。

### R-02 信息发布与管理

- 用户可以发布“丢失物品”或“拾到物品”信息。
- 信息至少包含类别、时间范围、地点范围、描述和当前状态。
- 用户可以查看、修改和关闭自己发布的信息。
- 图片支持 JPG、PNG、WebP，单张默认不超过 5MB、每条记录最多 3 张；保留和内容审核规则仍需确认。

### R-03 浏览和搜索

- 用户可以按关键词、类别、时间、地点和状态进行浏览或筛选。
- 默认不展示已经失效或被隐藏的信息。
- 搜索无结果、条件无效和服务异常时均有明确反馈。

### R-04 候选匹配

- 系统可以为失物或拾物信息提供候选记录。
- 候选结果显示主要匹配依据，不只给出不透明分数。
- 用户可以标记候选为“有帮助”“不相关”或“已确认”。
- 匹配结果只作为建议，不能自动判定所有权。

### R-05 状态闭环

- 发布者可以将信息标记为进行中、已找回、已归还或已关闭。
- 关闭时可以记录原因，涉及个人信息的备注不公开展示。
- 状态变化应保留必要的审计信息，具体保留期限待确认。

### 当前实现与建议范围对照

| 需求 | 截至 2026-10-06 的事实 | 尚缺内容 |
| --- | --- | --- |
| R-01 用户身份 | 前后端已实现本地账号注册、登录、会话恢复、注销、当前用户、普通/管理员角色、账号限制和资源归属检查基础 | 校园身份供应商、游客范围、管理员授予流程和账号恢复待确认 |
| R-02 信息发布与管理 | 前后端已实现详情、图片上传、发布、个人记录、编辑、关闭、归属校验和状态审计 | 对象存储、文件保留/删除策略和完整内容审核 |
| R-03 浏览和搜索 | 首页使用 `GET /api/v1/items` 查询 MySQL，支持关键词、类别、校区、时间和类型筛选、分页及详情 | 前端状态筛选与权限控制等仍需评审 |
| R-04 候选匹配 | 后端已实现规则候选生成、解释维度、站内通知、已读及确认/拒绝反馈，并提供校准任务和版本生命周期 | 真实标注数据、异步评估、站外通知和高级匹配模型 |
| R-05 状态闭环 | 前后端已实现失物“已找回”、拾物“已归还”、通用“已关闭”、归属校验和状态审计 | 认领核验流程与数据保留规则 |

详情页举报会进入后端审核队列；管理员可以驳回、解决或隐藏内容，用户限制和校准版本操作都会留下审计记录。完整认领核验和数据保留策略仍需产品评审。

## 5. 第一阶段不包含

- 支付、悬赏金托管或交易功能
- 对物品所有权作出自动裁定
- 面向多个学校的复杂租户管理
- 实时聊天系统
- 未经评审的面部识别或其他高风险生物识别能力
- 完全依赖 AI、无法人工核验的自动处理流程

## 6. 通用验收标准

每个功能 Issue 还应有自己的具体标准。第一阶段至少满足：

- 用户不能修改或关闭他人的信息。
- 必填字段在前后端都能得到有效校验。
- 正常、空状态、无权限、参数错误和服务异常均有明确结果。
- 关键操作有自动测试，主要用户流程有可重复的验收步骤。
- 接口、数据库结构或环境变量发生变化时，相应文档同步更新。
- 日志不记录密码、访问令牌或不必要的个人信息。

## 7. 非功能要求

- **安全**：遵循 [安全说明](../operations/security.md)，敏感配置不得进入仓库。
- **可访问性**：核心流程可以通过键盘操作，表单字段具有明确标签和错误提示。
- **兼容性**：支持范围在前端初始化时明确并写入 `frontend/README.md`。
- **性能**：在有代表性的数据量和部署环境确定后，再设定可测量的响应时间指标。
- **可维护性**：业务规则放在明确的模块中，功能与测试、文档共同交付。

## 8. 待团队确认

- 游客是否可以查看信息以及能够查看哪些字段。
- 校园身份如何验证。
- 图片是否必填、生产使用何种对象存储、保存多久。
- 联系方式如何保护，何时允许对方查看。
- 地点使用文本、校园区域还是地图坐标。
- 匹配使用规则、向量检索或外部 AI 的优先级。
- 数据保存、删除和账号注销策略。
