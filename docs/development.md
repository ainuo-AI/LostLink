# 开发流程

本文说明一项需求从提出到合并的默认流程。具体分支、提交和 Pull Request 规则见 [CONTRIBUTING.md](../CONTRIBUTING.md)。

## 1. 需求确认

每个开发任务开始前应明确：

- 要解决的问题
- 输入和输出
- 涉及的角色与权限
- 正常流程和异常流程
- 可验证的验收条件

## 2. 接口先行

前后端共同确认接口路径、请求字段、响应字段、状态码和错误格式，再分别实现。

接口草案统一放入 `docs/api/`，未评审的草案不得视为稳定契约。

涉及数据库结构变化时，还应同时提交 migration 设计，流程见 [database.md](database.md)。

## 3. 小步实现

一次只完成一个可独立验证的模块。功能代码、测试和对应文档应在同一个 Pull Request 中交付。

## 4. 验证

提交前至少完成：

- 格式和静态检查
- 单元测试
- 接口或页面的关键路径检查
- 异常和边界场景检查
- 文档同步检查

## 5. 合并

Pull Request 通过评审和自动检查后再合并到 `main`。合并后删除已经完成的短期分支。

## 看板状态

推荐使用以下状态，团队可以在 GitHub Projects 或其他项目管理工具中配置：

1. `待确认`：需求、范围或验收条件仍需讨论。
2. `待开发`：需求已确认，可以领取。
3. `开发中`：已有负责人正在实现。
4. `待评审`：Pull Request 已创建并可评审。
5. `待验证`：代码评审完成，等待功能验收。
6. `已完成`：满足完成标准并已合并。

任务被阻塞时保留原状态并添加 `blocked` 标记，在 Issue 中说明阻塞原因、负责人和下一步。

## 文档同步规则

- 用户行为或范围变化：更新 `requirements.md`。
- 模块职责或依赖方向变化：更新 `architecture.md`，必要时新增 ADR。
- 接口变化：更新 OpenAPI 定义和 `docs/api/` 中的说明。
- 数据结构变化：提交 migration，并更新 `database.md` 中的数据字典。
- 启动、测试或部署命令变化：更新对应说明，不保留无法执行的旧命令。
