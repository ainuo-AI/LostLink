# 测试策略

> 状态：前端已配置 Vitest；后端已配置 pytest，并覆盖健康检查、OpenAPI、物品列表接口和 MySQL Repository。浏览器端自动化测试尚未配置。

## 测试目标

- 证明需求验收条件已经满足。
- 尽早发现业务规则、权限、接口契约和数据库变化中的回归。
- 让测试失败能够指出具体问题，而不是依赖一次性人工演示。

## 测试分层

| 层级 | 关注内容 | 建议位置 |
| --- | --- | --- |
| 后端单元测试 | Service、匹配规则、校准规则和工具函数 | `backend/tests/` |
| 后端集成测试 | API、权限、Repository、数据库 migration | `backend/tests/` |
| 前端单元测试 | 组件、Store、格式化和校验逻辑 | `frontend/tests/` |
| 契约测试 | 请求、响应、状态码和错误格式与 OpenAPI 一致 | 前后端测试目录 |
| 端到端测试 | 发布、搜索、匹配反馈和关闭信息等核心流程 | 框架确定后指定目录 |

## 当前前端测试

在 `frontend/` 目录执行：

```bash
npm test
npm run type-check
npm run build
```

Vitest 当前覆盖查询参数序列化、FastAPI 错误转换、接口数据到页面模型的转换和时间显示格式。类型检查与生产构建用于发现组件类型和打包问题，但不能代替浏览器端端到端测试。

## 当前后端测试

在 `backend/` 目录执行：

```bash
uv run pytest
```

默认测试使用 FastAPI 测试客户端和内存演示仓储，不连接个人数据库，也不会调用外部服务。设置 `TEST_DATABASE_URL` 后执行 `uv run pytest -m mysql`，可以针对已迁移并写入演示数据的隔离 MySQL 验证正式 Repository。

Alembic migration 还需要在一次性数据库中验证 `upgrade head → downgrade base → upgrade head`。不得使用包含有效数据的共享数据库执行破坏性回滚测试。

## 每个功能至少验证

- 一条正常路径。
- 必填项为空、格式错误和边界值。
- 未登录、无权限和资源不存在。
- 重复提交、依赖服务失败或超时。
- 与本次修改相关的历史行为没有回归。

涉及匹配策略时，使用固定数据集验证排序、阈值和解释字段，避免测试依赖实时外部 AI 输出。

## 测试数据

- 测试数据由 fixture 或工厂创建，不依赖个人本地数据库。
- 自动测试不得调用真实付费服务或向真实用户发送通知。
- 示例账号、图片和位置不得包含真实个人信息。
- 每个测试独立清理状态，不能依赖执行顺序。

## Pull Request 验证记录

作者应在 Pull Request 中写明：

- 执行过的自动检查及结果。
- 未执行的检查及原因。
- 需要评审者手工验证的步骤。
- 涉及界面时的关键状态截图或录屏。

## 合并门槛

- 与改动相关的自动测试通过。
- 新增业务规则具有对应测试。
- 修复缺陷时，优先增加能够复现该缺陷的回归测试。
- 暂时跳过的测试必须关联 Issue，并说明恢复条件。
- 不以降低断言质量或删除有效测试来换取通过。

覆盖率可用于发现测试空白，但不能单独代表质量。团队应在工程初始化和首批测试稳定后，再确定合理的覆盖率门槛。
