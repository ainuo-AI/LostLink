# 架构边界

> 状态：前端原型已验证，后端架构仍为计划
>
> 最后验证：2026-09-21

本文同时记录当前已实现的前端结构和团队规划中的整体架构。后端及外部服务仍未实现，重大调整应通过 [ADR](adr/README.md) 记录。

## 当前实现

仓库目前只有可运行的前端首页原型。前端使用 Vue 3、TypeScript 和 Vite，数据来自 `HomeView.vue` 中的虚构数组，没有通过 HTTP 请求后端。

```text
index.html
    ↓
src/main.ts
    ↓
App.vue
    ↓
HomeView.vue
    ├─ SiteHeader.vue
    ├─ ItemCard.vue
    └─ ItemDetailDialog.vue
```

当前首页的数据流为：

1. `HomeView.vue` 持有演示记录和筛选状态。
2. Vue `computed` 根据关键词、类别、校区、区域、时间和记录类型计算可见结果。
3. 父组件通过 Props 向卡片和弹窗传递记录，子组件通过 Emit 通知父组件打开或关闭详情。
4. `src/types/item.ts` 统一记录、校区和区域的 TypeScript 类型。

`src/api/`、`src/router/`、`src/stores/` 和 `src/layouts/` 目前只是预留目录，不应视为已实现能力。

## 计划的总体结构

LostLink 计划采用以下前后端分离结构：

```text
Vue 3 前端
    ↓ HTTP API
FastAPI 接口层
    ↓
服务层
    ↓
数据访问层
    ↓
MySQL
```

浏览器只访问前端和公开 API，不直接访问数据库或第三方服务。第三方 AI、地图、对象存储和通知能力统一由后端适配，避免密钥进入浏览器。

## 核心业务边界

- **身份与权限**：识别用户、控制数据访问，不承载失物匹配逻辑。
- **信息发布**：管理失物与拾物记录、图片和状态，不直接决定匹配结果。
- **搜索与匹配**：根据结构化信息生成候选关系，只提供建议，不代表物品归属已经确认。
- **认领与反馈**：记录候选确认、拒绝、关闭等反馈，为后续策略校准提供输入。
- **外部集成**：封装 AI、地图、存储和通知供应商，业务层不依赖供应商私有字段。

匹配、反馈校准以及外部服务接入保持独立边界，避免直接散落在接口或页面中。

上述 FastAPI、MySQL、Alembic、匹配、校准和外部服务均尚未实现；具体认证方案、ORM、状态管理库、UI 组件库和部署平台也尚未确定。

## 后端分层约束

- 接口层负责参数接收、权限入口和响应组织。
- Schema 负责输入输出结构及校验。
- Service 负责编排业务流程。
- Repository 负责数据库读写。
- Model 只表达持久化结构和关系。
- Matching 只负责候选匹配与评分策略。
- Calibration 只负责基于反馈调整策略。
- Integration 负责隔离外部 AI、地图和通知服务。
- Task 负责异步或后台执行入口。

## 前端分层约束

- View 负责页面组合，不直接散布底层请求细节。
- Component 负责可复用界面单元。
- API 统一封装后端调用。
- Store 只保存跨页面共享状态。
- Router 维护页面导航和访问边界。
- Type 维护共享数据结构。

当前原型已按 View、Component、Style 和 Type 进行分层。API、Store、Router 和 Layout 层要在出现实际需求时再引入，不提前声称已完成。

## 当前边界

- 用户认证与权限实现
- 失物或拾物发布功能
- 后端搜索、候选匹配和推荐算法（当前只有浏览器内的演示数据筛选）
- AI 特征提取
- 数据库模型与迁移脚本
- 通知、地图和文件上传
- 可运行的后端工程配置
- 自动化单元测试和端到端测试

## 计划的主要数据流

1. 用户通过前端提交失物或拾物信息。
2. API 完成身份校验、参数校验和权限检查。
3. Service 编排业务规则，通过 Repository 持久化数据。
4. Matching 根据已确认的数据生成候选匹配及可解释的评分信息。
5. 用户反馈候选结果，Calibration 消费反馈并调整后续策略。
6. 需要外部能力时，由 Integration 调用供应商并统一处理超时、失败和降级。

## 依赖规则

- 接口层可以调用 Service，不直接读写数据库。
- Service 可以依赖 Repository、Matching 和 Integration，不依赖具体页面。
- Repository 只处理持久化，不实现业务流程。
- Matching 不直接发送通知或修改用户数据。
- 外部服务响应必须转换为项目内部类型后再进入业务层。
- 跨层共用的数据结构要有唯一来源，避免前后端各自维护互相冲突的定义。

## 技术选择

| 范围 | 当前选择 | 理由 | 状态 |
| --- | --- | --- | --- |
| 前端 | Vue 3 | 组件化、生态成熟，适合课程项目协作 | 待 ADR 确认 |
| 后端 | FastAPI | 类型提示和自动 OpenAPI 支持较好 | 待 ADR 确认 |
| 数据库 | MySQL | 适合结构化业务数据和事务场景 | 待 ADR 确认 |
| 数据迁移 | Alembic | 与 Python 后端及 SQLAlchemy 生态匹配 | 待后端初始化确认 |

选择某项技术不等于默认引入其全部生态。状态管理、UI 组件库、ORM、任务队列和部署平台应在实际需求明确后单独评估。
