# 运行手册

> 状态：未上线。下文的故障流程是待演练规范；当前只提供本地开发环境的已知排查入口，值守、监控和生产恢复命令仍待确定。

## 用途

运行手册供值守者在告警或用户报告问题时快速判断影响、降低损失并恢复服务。它不是架构设计文档，内容必须简短、可执行并经过演练。

## 故障处理流程

1. **确认影响**：哪些用户、功能和环境受影响，问题从何时开始。
2. **控制影响**：暂停有风险的发布、任务或外部调用，必要时启用降级。
3. **收集证据**：记录版本、错误、指标和时间线，不在公共渠道粘贴敏感数据。
4. **恢复服务**：选择回滚、向前修复、扩容或隔离故障依赖。
5. **验证恢复**：执行健康检查和核心流程冒烟测试。
6. **复盘改进**：记录根因、影响、有效措施和后续 Issue，不以追责个人为目的。

## 首要检查项

- 最近是否有应用、配置或数据库变更。
- 健康检查是否正常，错误率和响应时间是否异常。
- 数据库连接、容量、锁和慢查询是否异常。
- AI、地图、存储、通知等外部依赖是否失败或限流。
- 后台任务是否积压或重复执行。
- 是否只有特定角色、浏览器、地点或数据受到影响。

## 常见场景

### 本地首页显示无法加载记录

1. 先区分影响范围：`/publish/lost`、`/publish/found` 和 `/notifications` 是浏览器本地演示，不依赖后端；首页列表依赖 FastAPI 和 MySQL。
2. 确认后端启动终端是否仍在运行，检查 `http://127.0.0.1:8000/health`，再检查 `http://127.0.0.1:8000/api/v1/items`。健康检查成功只能证明应用在运行，不能证明数据库查询正常。
3. 在 `backend/` 检查 `docker compose ps mysql` 和 `uv run alembic current`，核对 `.env` 中的 `DATABASE_URL`；前端核对 `VITE_API_BASE_URL`。修改 `.env` 后重启对应服务。
4. 后端恢复后点击首页“重新加载”。若本地演示表单或通知读取失败，查看页面错误提示；不要为了排障直接清空浏览器站点数据，因为草稿、图片和处理状态会一起丢失。

以上是当前本地路由、配置和启动命令对应的排查顺序，不是已经演练的生产恢复方案。

### API 大量失败

- 确认失败接口、状态码和开始时间。
- 检查最近发布与数据库 migration。
- 检查数据库和外部依赖状态。
- 若新版本导致且无法快速修复，执行应用回滚。

### 数据库 migration 失败

- 停止继续发布，不重复盲目执行。
- 保存失败 revision、错误和数据库状态。
- 判断 migration 是否部分执行以及应用版本是否兼容。
- 依据已评审方案向前修复或回滚；涉及数据删除时必须先确认备份。

### 外部 AI 或地图服务不可用

当前没有这些外部服务集成；以下仅为将来接入后的处理原则。

- 核实是否为超时、限流、额度或认证问题。
- 停止无上限重试，启用超时、退避和熔断。
- 保留基础发布和搜索功能，明确提示增强能力暂不可用。

### 疑似敏感数据泄露

- 立即限制相关访问并停止继续记录或传播数据。
- 保存必要证据，但不要在普通 Issue 中粘贴密钥或个人信息。
- 轮换可能暴露的凭据，检查访问日志和影响范围。
- 按 [security.md](security.md) 的私密渠道通知负责人。
