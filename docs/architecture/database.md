# 数据库与迁移

> 状态：四份 migration 已演进出认证、物品、图片、举报、通知、审计和校准结构；最新版本 `20261006_0004` 已在本地 MySQL 完成升级。完整回滚仍只允许在一次性数据库验证。
>
> 文档核对：2026-10-10；真实 MySQL migration 验证记录：2026-10-06。

## 目标

数据库结构必须通过版本化 migration 演进，使开发、测试和部署环境可以从同一基线得到一致结构。已经合并或在共享环境执行过的 migration 不得直接改写；需要修正时创建新的 migration。

## Migration 工作流

1. 在 Issue 或设计文档中说明数据变化及兼容性影响。
2. 更新数据模型，并生成或手写 migration。
3. 人工检查生成结果，特别是字段删除、类型转换、唯一约束和索引。
4. 在空数据库上执行全部升级。
5. 在包含代表性旧数据的数据库上执行升级并验证数据。
6. 验证回滚；无法安全回滚时，在 migration 和部署说明中明确标注。
7. 在同一个 Pull Request 中更新测试、数据字典和部署说明。

已经验证的升级、查看版本、查看历史和回滚命令维护在 [backend/README.md](../../backend/README.md)。

## 命名与编写要求

- 文件名和 revision message 描述一个明确变化，例如 `add_item_status_index`。
- 一个 migration 尽量只处理一个相关变更。
- 表名和字段名使用统一的 `snake_case`。
- 外键、唯一约束和索引使用可读且稳定的名称。
- 不在 migration 中调用不稳定的外部服务。
- 大数据更新要分批执行，并评估锁表、磁盘和执行时间。
- 删除字段或表采用“停止写入 → 迁移数据 → 停止读取 → 删除”的分阶段方式。

## 数据字典

### `items`

用途：保存公开的失物与拾物记录。时间统一以 UTC 写入 MySQL `DATETIME(6)`，API 返回时恢复为带时区的 ISO 8601 字符串。

| 字段 | 类型 | 可空 | 说明 |
| --- | --- | --- | --- |
| `id` | `BIGINT` | 否 | 自增主键 |
| `owner_id` | `BIGINT` | 是 | 发布者用户外键；历史演示数据可为空，新写入流程应强制关联当前用户 |
| `type` | `VARCHAR(16)` | 否 | `lost` 或 `found` |
| `category` | `VARCHAR(50)` | 否 | 物品类别 |
| `title` | `VARCHAR(120)` | 否 | 记录标题 |
| `description` | `TEXT` | 否 | 公开描述 |
| `location` | `VARCHAR(120)` | 否 | 具体地点文本 |
| `campus` | `VARCHAR(20)` | 否 | 东丽校区或宁河校区 |
| `area` | `VARCHAR(20)` | 是 | 东丽校区为北区或南区；宁河校区为空 |
| `occurred_at` | `DATETIME(6)` | 否 | 物品丢失或拾到时间，按 UTC 解释 |
| `status` | `VARCHAR(16)` | 否 | `active`、`recovered`、`returned` 或 `closed` |
| `contact_hint` | `VARCHAR(255)` | 否 | 兼容旧版的联系说明字段 |
| `contact` | `VARCHAR(255)` | 是 | 完整联系方式，在公开记录中直接展示；历史记录为空 |
| `contact_note` | `VARCHAR(200)` | 是 | 发布者填写的公开联系与核验说明 |
| `storage_method` | `VARCHAR(16)` | 是 | 拾物保管方式：`self` 或 `office` |
| `storage_location` | `VARCHAR(100)` | 是 | 拾物保管地点 |
| `contact_window` | `VARCHAR(100)` | 是 | 拾物可联系时间或范围 |
| `closure_reason` | `VARCHAR(255)` | 是 | 完成或关闭原因，不进入公开响应 |
| `closed_at` | `DATETIME(6)` | 是 | 进入终态的 UTC 时间 |
| `created_at` | `DATETIME(6)` | 否 | 数据创建时间 |
| `updated_at` | `DATETIME(6)` | 否 | 最近更新时间 |

约束与索引：

- 检查记录类型、状态、校区以及校区与区域的合法组合。
- 检查 `storage_method` 只能为空、`self` 或 `office`；更完整的跨字段规则由 Service 执行。
- `status + occurred_at + id` 复合索引支持默认列表的筛选和稳定排序。
- 类型、类别以及校区与区域组合具有辅助筛选索引。
- 表使用 `utf8mb4` 和 `utf8mb4_0900_ai_ci`，满足中文及 emoji 存储和不区分大小写搜索。

历史演示数据允许 `owner_id` 与联系方式等字段为空；所有新发布记录由后端强制关联当前用户。完整联系方式在公开记录中直接展示，不写入日志。

### `users`

用途：保存本地账号、角色、账号状态、校园验证标志以及登录失败保护状态。密码只保存带随机盐的 scrypt 摘要。`account` 唯一；角色为 `user` 或 `admin`，状态为 `active` 或 `restricted`。

### `auth_sessions`

用途：保存服务端可吊销会话。表内只保存随机 Bearer 令牌的 SHA-256 摘要、用户外键、过期时间和吊销时间；删除用户时级联删除其会话。`user_id + expires_at` 索引用于按用户清理过期会话。

### `item_status_history`

用途：不可变地保存每次成功状态转换，包括物品、操作者、原状态、新状态、原因和时间。删除物品时级联删除其历史；用户删除策略尚未确定，因此审计记录当前会阻止直接删除仍被引用的操作者。

### 新增业务表

| 表 | 用途与关键约束 |
| --- | --- |
| `stored_images` | 保存图片所有者、关联物品、MIME、大小、SHA-256 和受控存储键；删除用户或物品时按外键清理 |
| `reports` | 保存举报原因、说明、待处理/驳回/解决/隐藏状态及处理管理员和时间 |
| `match_notifications` | 保存收件人、源物品、候选物品、综合分、解释维度、已读和反馈；同一收件人的物品对唯一 |
| `admin_audit_logs` | 不可变保存管理员动作、对象、理由和允许记录的结构化详情 |
| `calibration_versions` | 保存匹配权重、评估指标以及草稿、批准、启用、拒绝和归档状态 |
| `calibration_tasks` | 保存评估日期范围、类别、执行状态、指标和候选版本关联 |

2026-10-10 的产品调整复用现有 `contact`、`contact_note`、`stored_images` 和通知字段，不需要新增 migration。匹配通知状态仍兼容历史 `confirmed`，新反馈仅允许 `rejected`；取消认领不创建认领表。

上传文件二进制默认保存在 `UPLOAD_DIRECTORY`，数据库只保存相对存储键。匹配解释、审计详情、权重和指标当前以 JSON 字符串保存，Repository 负责序列化与解析，API 不暴露内部字符串格式。

后续新增表时，每张表至少说明：

| 内容 | 说明 |
| --- | --- |
| 用途 | 该表保存什么业务信息 |
| 主键 | 主键类型和生成方式 |
| 字段 | 类型、是否可空、默认值及业务含义 |
| 关系 | 外键和删除策略 |
| 约束 | 唯一约束、检查约束 |
| 索引 | 索引用途和对应查询 |
| 敏感性 | 是否包含个人或敏感数据 |
| 生命周期 | 保存、归档和删除规则 |

## 审查清单

- [ ] 新代码是否兼容 migration 执行前后的短暂状态
- [ ] 是否可能丢失或错误转换已有数据
- [ ] 是否需要新增索引，索引是否会影响写入
- [ ] 是否验证升级和回滚路径
- [ ] 是否更新测试、数据字典和备份要求
- [ ] 日志和错误信息是否可能暴露敏感数据

## 禁止事项

- 不手工修改共享环境结构来替代 migration。
- 不因为开发环境没有数据就跳过兼容性检查。
- 不把数据库密码、备份或生产数据提交到 Git。
- 未确认备份和恢复能力前，不执行不可逆的批量删除。
